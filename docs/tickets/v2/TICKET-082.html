TICKET-082

A password reset or change ends the user's other sessions

OpenPriority: High

Summary

Today, resetting or changing a password leaves every existing session alive. A stolen 30-day refresh cookie, and any realtime connection opened with it, keeps working after the owner has "secured" their account.

This ticket makes both flows end the other sessions:

  • A reset ends every session.
  • A change ends every session except the device making it.
  • Both drop the user's live realtime connections.
  • A successful reset also kills any older reset links still sitting in the inbox.

In one sentence: after a password reset or change, the only sessions left are ones the owner just created.

What came before. The April auth system introduced the two-token model: a 15-minute access token held in memory, and a 30-day refresh token in an httpOnly cookie, stored server-side as a digest that can be revoked. TICKET-015 added password reset by email. TICKET-023 authenticated the realtime connection with that same refresh cookie. PR #86 rate-limited sign-in, registration and reset. Only logout ever revokes a refresh token today, and only the current device's.

What this unlocks. Rotating refresh tokens with reuse detection (pre-production list item 4) needs a "revoke this user's sessions" operation. This ticket builds it. Rotation will reuse it to revoke a whole token family on replay.

Mental model: Devise's "sign out everywhere on password change", built on our own refresh_tokens table: a scoped update_all(revoked_at: …), keeping one row back.

What you're building

extendapi/app/models/user.rb
Owns "end this user's sessions". It revokes the user's usable refresh tokens, optionally keeping one (the device making the change), and disconnects the user's open realtime connections. One operation, called from both flows, so they can't drift. Rotation will call it later too.
extendapi/app/controllers/api/v1/password_resets_controller.rb
On a successful reset, end every session and consume every active reset token for the user, not just the one used. Requesting a new link still leaves older links alone. The response contract is unchanged.
extendapi/app/controllers/api/v1/profile/passwords_controller.rb
On a successful change, end every session except the one whose refresh cookie came with the request. The success message tells the user that other devices were signed out, and the server owns that copy.
componentclient/src/components/me/ChangePasswordDialog.tsx
Shows the server's success message in the toast instead of the hardcoded "Password updated", so the user learns their other devices were signed out.
PATCH /password_resets/:token (success) ├─ user.end_sessions(keep: none) → all refresh tokens revoked │ → user's cable connections dropped └─ all active reset tokens consumed PATCH /profile/password (success) └─ user.end_sessions(keep: this request's refresh cookie) → other devices revoked + dropped; this device's socket reconnects

No migration, no new endpoints, and no change to any response shape. The method name in the diagram is illustrative.

Requirements

  1. A reset ends every session. After a successful password reset, none of the user's refresh tokens can mint an access token, so every device is signed out at its next refresh.
  2. A change ends every other session. After a successful password change, every refresh token except the current device's is revoked. The current device stays signed in without noticing.
  3. Live connections drop. Both flows disconnect the user's open realtime connections. Revoked devices can't reconnect. The current device reconnects on its own after a change.
  4. One reset link works once, for all links. A successful reset consumes every active reset token the user has, so an older email's link returns 410. Requesting a new link doesn't invalidate older ones. Decision (12 Nov): this avoids racing a user who's mid-click on the first email.
  5. Failures change nothing. A wrong current password, a validation error, or an expired or used reset link revokes nothing.
  6. The user is told. The success copy for a password change says other devices were signed out. The server owns the wording, and the toast shows it.

States, access, cache

  • Access: unchanged. Reset is unauthenticated by token; change requires the current password. A user can only ever revoke their own sessions.
  • Access tokens: those already issued keep working until they expire (up to 15 minutes), because access tokens are stateless by design (auth doc §5.4). Out of scope.
  • Cache: no client cache changes. A revoked device finds out at its next refresh, when the 401 sends it to login through the existing path.

Acceptance criteria

Sign in on two browsers. Reset the password via the email link. Both browsers end up at login on their next refresh, or on reload. (UI)
After a reset, POST /token with any of the user's pre-reset cookies returns 401. (test)
Sign in on two browsers. Change the password on browser A. A stays signed in, its toast says the other devices were signed out, and B is sent to login on its next refresh. (UI)
After a change, the request's own refresh token is still usable and every other token for that user is revoked. Other users' tokens are untouched. (test, data)
A change made without a refresh cookie (access token only) revokes all of the user's refresh tokens. (test)
Both flows disconnect the user's realtime connections. The test asserts the disconnect is requested for that user, and only that user. (test)
Request two reset emails, then use the newer link: the older link returns 410. Request two, use neither: both still work. (UI, test)
A wrong current password, a too-short new password, or an expired link revokes nothing and consumes nothing. (test)

Getting the mutation's response into onSuccess. In ChangePasswordDialog, useFormSubmit's onSuccess runs after the action but doesn't receive what mutateAsync resolved with. To toast the server's message, capture the resolved value inside the action (a local variable or a ref) and read it in onSuccess. A ref fits here, because the dialog already uses rejectedRef for the same "action → onSuccess" handoff, and a ref changing doesn't re-render.

Notes & gotchas

  • What exists today:
    • The only revocation is SessionsController#destroy → refresh&.revoke! (sessions_controller.rb:19).
    • Reset consumes one token (password_resets_controller.rb:31). Change revokes nothing (profile/passwords_controller.rb:12).
    • User has_many :refresh_tokens, :password_reset_tokens. PasswordResetToken.active already scopes to unused, unexpired tokens.
  • The current device's cookie reaches the change endpoint. The cookie's path is /api/v1, so PATCH /api/v1/profile/password carries it. Use RefreshToken.find_by_raw_token(cookies[:refresh_token]) to identify the token to keep, and don't trust a token id from the request body.
  • Disconnecting the cable. ActionCable.server.remote_connections.where(current_user: user).disconnect works because the connection is identified_by :current_user. It goes through the cable's pub/sub, which is Redis in dev (see memory: ActionCable dev setup). In tests, assert that the disconnect is requested rather than expecting a real socket to close.
  • Use update_all for the bulk revoke, scoped to the user and to still-usable tokens, so revoked rows keep their original revoked_at. The RuboCop SkipsModelValidations directive is warranted here, like the counter caches.
  • Revoke after the password saves, not before. A validation failure has to leave every session intact (requirement 5).
  • Out of scope: refresh rotation and reuse detection (pre-production list item 4); revoking access tokens already issued (§5.4); purging old token rows; a "sign out everywhere" button on Me (not planned).
  • After merge: run /sync-tech-design-doc on the auth doc to move these two gaps out of §9 and into §5.6 and §5.8.

TICKET-083

API CI green and patched: Ruby 3.4.12 + Rails 8.1.4.1 security bump

OpenPriority: High

Summary

API CI is red on every PR, for two unrelated reasons:

  • GitHub's ubuntu-latest runner image moved to 26.04, and there's no prebuilt Ruby 3.4.8 for it. Every Ruby job dies at setup.
  • The security audit now flags Rails 8.1.3.1 itself, plus rack and a handful of HTML/URL gems, with one Critical and five Highs.

This ticket moves Ruby to 3.4.12 (what dev already runs) and pins it in Docker so dev and CI can't drift apart again. It then bumps the flagged gems to their patched versions.

In one sentence: CI runs again, and it runs on a Rails with no known Critical or High advisories.

What came before. The July security review found no code-level holes, but flagged gem advisories (erb, faraday, jwt) as their own ticket. Those have since been superseded by a bigger set against the Rails framework itself. The last green API CI run on main was 2026-09-11. What this unlocks. PR #109 (TICKET-082) can't go green until this merges and it rebases. The same holds for TICKET-081 and every later API PR. It also clears an infra item on the pre-production list.

Mental model: a routine bundle update rails --conservative patch-release bump, plus fixing a .ruby-version that had quietly become fiction.

What you're building

Today they disagree: CI wants 3.4.8, and dev gets whatever ruby:3.4 floats to, currently 3.4.12. After this ticket both say 3.4.12, and the Docker image no longer floats.

Moves the flagged gems to their fixed versions:
  • Rails 8.1.3.1 → ≥ 8.1.4.1, which carries actionpack, actionview, activestorage, activesupport and actionmailbox;
  • rack 3.2.7 → ≥ 3.2.8;
  • nokogiri → ≥ 1.19.5, loofah → ≥ 2.25.3, rails-html-sanitizer → ≥ 1.7.2, crass → ≥ 1.0.8;
  • addressable → ≥ 2.9.1.
The Gemfile's ~> 8.1.2 already allows 8.1.4.1, so this should be a lockfile-only change.
commit 1 ruby 3.4.8 → 3.4.12 (.ruby-version + Dockerfile pin) → CI can set up Ruby commit 2 bundle update (targeted, conservative) → bundler-audit green

No application code should change. If a patch release forces one (a deprecation, a changed default), it's its own small commit with a test.

Requirements

  1. CI sets up Ruby on the current runner image. Every job in both workflows gets past "Set up Ruby" on ubuntu-latest, without pinning the runner to an older Ubuntu.
  2. Dev and CI run the same Ruby. Docker's Ruby and .ruby-version name the same exact version, and a Docker rebuild can no longer change it silently.
  3. The audit is clean. bundler-audit check --update reports no advisories: Critical, High, Medium or Low.
  4. Only what needs moving moves. The lockfile diff is limited to the flagged gems and the dependencies they drag along. No unrelated major-version jumps.
  5. Behaviour is unchanged. The full API and client suites pass, and the test log shows no new deprecation warnings.

Why these advisories matter here specifically

  • activestorage, Critical (GHSA-f3w6-w445-fwh9): arbitrary file write and read during image analysis. We analyse every upload. PlantPhoto has_one_attached :image and User has_one_attached :avatar, processed by image_processing with libvips.
  • actionpack, High (GHSA-2gff-2mmg-m73p): IP spoofing in ActionDispatch::RemoteIp. Our Rack::Attack throttles key on exactly that resolved IP (auth doc §5.9). A spoofable IP makes the per-IP login and reset limits bypassable.
  • actionpack, High (GHSA-wm3x-v3qw-4jh3): a strong-parameters bypass in Parameters#each_key. Every controller filters input through params.expect.
  • activesupport and rack, High: DoS (safe_constantize, multipart memory exhaustion). The multipart one is the photo-upload path again.

Notes & gotchas

  • What exists today:
    • api/.ruby-version has said ruby-3.4.8 since the initial commit. api/Dockerfile:1 is FROM ruby:3.4, which resolves to 3.4.12 today.
    • Both workflows use ruby/setup-ruby@v1 with working-directory: api, so they read .ruby-version.
    • ruby/ruby-builder publishes 3.4.12 for ubuntu-26.04 (x64 and arm64). 3.4.8 has no 26.04 build.
  • Don't pin runs-on to ubuntu-24.04 to dodge requirement 1. It would work today, but it defers the same failure to when 24.04 is retired, and it leaves the dev/CI drift in place.
  • Rebuild the images after the Dockerfile change: docker compose build api sidekiq, then ./scripts/bundle.sh if gems are vendored in a volume. Old containers will keep running the old Ruby until you do.
  • Update conservatively. Name the flagged gems (rails rack nokogiri loofah rails-html-sanitizer crass addressable) and use --conservative, so Bundler moves only what it must. If the update pulls in a gem outside that list, read why before accepting it.
  • CI's cache key hashes .ruby-version and Gemfile.lock (api.yml:56), so the first run after this rebuilds the RuboCop and bundler caches. Expect it to be slower.
  • After merge: rebase #109 (TICKET-082) and the TICKET-081 branch onto main so their CI runs on the fixed Ruby.
  • Out of scope: setting trusted_proxies, and the other production configuration (pre-production list); bumping gems beyond the patched versions; moving to Ruby 3.5.
  • When you're done: run the pre-commit gate from CLAUDE.md (tests + typecheck → comment audit → review triad → ./scripts/lint.sh last), commit on a feature branch, then open a PR.
